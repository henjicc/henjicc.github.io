# 架构与代码组织

> 读取时机：引入抽象、通用封装或依赖，改变模块职责、依赖方向、公共契约、存储格式、状态归属或跨层边界时。

## 职责与权威入口

- 同一业务规则、schema、状态和能力定义只维护一个权威来源，其他入口通过委托或派生复用。
- 展示负责呈现和输入，核心规则不依赖具体 UI；外部存储、网络和供应商细节放在明确边界。分层结构只在实际复杂度需要时引入。
- 临时 UI 状态留在局部；共享与持久化状态明确权威修改者，派生缓存明确失效和重建条件。
- 仅外形相似、变化原因不同的代码不强行合并；不为消除少量重复引入更多模式参数和条件分支。公共接口按真实消费者需要保持最小。

## 跨进程边界

- 有远端服务时通过明确 API / schema 通信；无远端服务不虚构后端。认证、校验和特权接口的可信位置见安全规则。
- 共享契约而非供应商响应或存储内部模型；边界负责转换及错误语义。

## 复用与依赖

- 复用顺序和“已有依赖能表达就不自研”按 `AGENTS.md` 的“复用优先”，查找与评估方法见研究规则。
- 简单局部逻辑优先直接表达或使用具名函数；不为单个简单分支建立注册表、策略框架或通用执行器，不增加无独立职责的透传包装层。
- 抽象应简化当前复杂逻辑、统一真实规则或隔离实际边界；差异确由数据或能力决定时再集中配置或策略。一次使用的辅助函数、单一实现的接口也可有这些价值，不机械按复用次数决定。
- 引入依赖还是自研按总成本比较：依赖计入集成、升级和替换成本，自研计入实现、边界处理和长期维护成本。第三方边界的隔离程度与实际风险匹配。

## 变更边界

- 高影响迁移先建立行为基线，迁移消费者后移除旧路径。
- 存储格式或公共契约变更明确版本、兼容范围和失败恢复，验证旧数据、部分完成和重复执行；不得以静默丢字段、重置用户数据或吞解析错误实现兼容。
- 长期且不易从代码推断的决策写入项目既有决策入口；局部细节不另建 ADR。

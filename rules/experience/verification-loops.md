# 验证闭环与代码评审

> 适用范围：搭建或调整测试体系、代码审查流程、提交门禁，以及让 AI 自行验证或多个 AI 并行工作。日常改动的验证范围仍按 [`testing.md`](../testing.md)。
> 来源：Claude Code 团队文章 [How the Claude Code team thinks about verification](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)（Addy Osmani，2026-11-16 发布），2026-11-17 对照原文提炼；“代码评审流程”一节来自 [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)（2026-10-15）。这是对方团队的做法，没有在本模板的项目里验证过。其中适用于日常改动的几条已写进 `testing.md`。

## 为什么值得投入

- 没有验证闭环时，人要亲自检查每一处改动，同时能带的 AI 只有一两个；有了闭环才谈得上放手和并行。
- 让 AI 有办法检查自己的产出，本身就能提高质量。原文的内部测试里，由独立的评分者按评分标准检查产出，任务成功率最多提高 10 个点，越难的任务收益越大。
- 测试、基准和规格现在可以让 AI 来写，写好后作为普通软件反复运行，几乎不再消耗 token。
- 失败要回流：同一类问题反复出现时，把它变成钩子或一条明确的规则。

## 优先建哪种测试

三种测试都要避免：不稳定（会教 AI 重跑而不是修代码）、太慢（每批能跑的少，问题更难定位）。重型测试放在提交前跑。

| 类型 | 做法 | 适合 |
|---|---|---|
| 端到端测试 | 描述真实用户流程，如加入购物车、结账、到达确认页 | 只能选一种时选它。整个功能要么通要么不通，很难蒙混；完成标准明确，失败时能给出截图和哪里坏了的描述，而单元测试可能只报一句超时 |
| 属性测试 | 先写一条认为不可能被打破的断言，再生成大量输入去证伪 | 编解码往返、不变量（如余额不为负）、幂等、优化版与朴素版等价。生成的边界情况不受写代码那个 AI 的偏见影响。重写旧系统、规格已经和线上行为不一致时尤其有用 |
| 差分测试 | 新旧系统跑同样的输入，任何差异都是缺陷或破坏性变更 | 行为应保持不变的大规模迁移。输入用随机生成或生产流量抽样，忽略空白等无关差异，有意的差异列入已批准清单 |

- 单元测试更快更稳，但可能在功能坏掉时照样通过。
- 端到端测试需要 AI 能启动、操作和观察运行中的应用。把启动和驱动方式写成一个技能，放在离相关代码最近的位置。
- 功能清单从用户视角列出每个功能的路径、快捷键、选择器和预期结果，既是操作指引，也是评分标准。

## 团队做法

- **验证就是把改动跑起来。** 端到端运行应用比只跑测试更重要。验证技能是冒烟测试的基础设施，要快、要可靠，值得反复打磨。
- **先跑便宜的检查。** 提交评审前先过测试、构建和 lint，不把没测过的代码推给共享的评审和 CI。
- **三轮修不好就停。** AI 运行检查并尝试修复；同一项检查连续三轮仍失败，停下来交给人。
- **改动不能修改评判自己的检查。** 评审规则从基准分支读取，不从改动本身读取。能被改动修改的检查等于没有检查。
- **只评审当前提交。** 评审期间有新推送，结果就作废。
- **一个评审者，多轮评审。** 不叠加第二个更贵的评审者，而是调好主评审者；每一轮沿用前几轮的上下文和失败记录，比每次从头检查便宜，也查得更多。
- **检查清单按 diff 触发。** 每条写明能从 diff 看出的触发条件、要检查什么、背后的事故。每次只跑触发条件命中的几条，不全量过一遍。
- **负责代码的人写自己的检查**，调到它会标出本人会标出的问题。检查上报给人时要写明原因。
- **提交标注验证方式**，没验证也如实写“无”，这样能查出未验证的提交。门禁先用观察模式记录本来会拦下什么，确认误报可接受后再开启拦截，并留出出口：提交信息里可以说明为什么没验证；同一会话被拦两次后放行下一次，避免 AI 卡死。
- **检查本身也要测。** 用被回滚的改动、合并前被否决的改动和规模相当的干净改动来评估：真问题抓到多少，干净改动误报多少。重要程度和是否正确分开打分，改动之前就存在的问题不算在作者头上。分阶段统计召回率（初步发现、复核后、最终评审），才能看出系统是否把已经找到的缺陷又弄丢了；召回率调到再提高就是迎合评测集为止。
- **把漏掉的问题变成规则。** 同一类问题在至少两个改动里出现、且能从 diff 识别，才值得写成规则；先让几个 AI 尝试证伪，再由人批准。另一种办法是拿已知事故对应的改动回放给几个找缺陷的 AI：多数能找到说明可检测，在小改动上仍然漏掉的才是值得补规则的缺口。
- **不稳定测试** 不允许跳过、加 sleep 或重试到通过。找不到根因就删掉这个测试并写明原因。
- **定期清理。** 测试集、验证步骤和规则文件只增不减就会失效，要例行精简。

## 代码评审流程

出发点是把问题从“有没有人读过代码”换成“这个改动可能出什么错，哪种检查最适合抓住它”。人的时间和注意力是稀缺资源，留给只有人能判断的事；衡量标准是每个改动消耗的人工时间，同时以回滚率和事故率为底线，这两项上升就说明人工时间只是被挪到了事后。

一个改动依次经过这些层，每层抓住一部分问题，漏掉的由最后的快速回滚兜底：

| 层 | 内容 |
|---|---|
| 提交评审前 | AI 运行测试、构建和 lint 并展示输出，而不是只说完成；再由一个全新上下文的子代理审查差异 |
| 必过的 CI | lint、类型、各平台测试、构建，失败即阻止合入 |
| AI 评审 | 多个代理并行找缺陷，另一组投票确认，只留下确认的并按严重度排序；纯风格和清理类意见直接丢弃 |
| 安全评审 | 单独一遍。任何未处理的发现都阻止合入：要么修，要么写明理由后关闭 |
| 按风险分级的人工批准 | 见下表 |
| 合并队列 | 在最新主干上叠加改动后重跑全部检查，防止两个各自通过的改动合起来出错 |
| 开关与灰度 | 新行为先放在开关后面给内部使用，再分渠道逐步发布 |
| 发现与回滚 | 作者和值班人盯着；开关可以不发版关闭；事故复盘问的是哪一层本该抓住它 |

| 风险 | 例子 | 需要的人工批准 |
|---|---|---|
| 低 | 文档、文案、仅内部功能、开关后面的纯新增 | 自动评审和安全检查通过后不需要 |
| 中 | 普通产品改动；缓存、自动更新、系统提示等敏感区域 | 一人 |
| 高 | 风险最高的代码和少数固定路径 | 两人 |

- 等级由改动决定，不由作者决定。鉴权、计费、CI 工作流、发布和安装程序这类路径始终需要人。
- AI 的批准不能顶替要求的人工批准。指挥 AI 写代码的人算作评审人之一，并对结果负责。
- 批准只对应一个具体提交，之后有新提交就要重新批准。
- 评审规则写给评审者看：这个仓库里什么算失败（文档是“说了假话”，配置是“路由错了”）、挑刺的上限、跳过哪些路径、要求给出文件和行号作为证据而不是凭名字猜。
- 评审必须收敛。AI 作者和 AI 评审者可以无休止地互相找事，原文里一个改动一夜之间来回了五十多轮，而评审者反复标出的大多是早就存在的代码。对策是：三轮后让作者退一步重新考虑方案；前几轮之后只复查新增差异；指出的是一类问题而不是一行，让作者一次修完所有同类；不重复已提过的意见。
- 对 AI 作者来说噪声代价更高：人可以几秒钟忽略一条挑刺，AI 会去改，于是多一次提交和一轮评审。
- 每次事故和回滚都加进评测集，评审者的提示、工具或模型有变化就重新打分；同时在确认干净的改动上统计它误报的次数。
- 人仍然负责：要不要做这件事；高风险代码和会被别人照抄的架构；阅读证据（测试输出、执行的命令及结果、截图）；对上线的每个改动负责。说不出这些检查会漏掉什么时，要求真正的评审而不是快速批准。
- 改动小、可撤销，是“谁合入谁负责”能成立的前提。
- 想了解某块代码时，让 AI 针对那一块写一份讲解，比逐行读琐碎的差异有用。

## 一句话

让验证层处在被评判的改动够不着的地方，用真正重要的缺陷来衡量它，漏了就记下来，记下来的东西定期清理。人的工作从逐行读 diff 变成定义什么算完成、审阅证据。

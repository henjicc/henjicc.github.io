# UI、设计系统与文案

> 读取时机：修改界面、样式、文案或交互时；只应用与本次变化相关的条款。

## 沿用系统与产品形态

- 沿用已确认的产品形态和设计系统；改变平台行为时再读取平台规则。
- 组件、图标、动画、布局、拖拽、状态管理等按项目上下文中按职责指定的库实现。指定库能正确表达时按“复用优先”直接使用，如下拉、弹窗、拖拽排序、可调整面板和动画调度都不手写；也不引入同职责的第二个库。缺少指定时按“复用优先”选型，给出一个推荐及简短理由，经用户确认后写入上下文。
- 优先选择组件源码进入项目、可直接修改的方案（如 shadcn/ui）；样式与行为在项目组件层定制，不在业务页面覆盖第三方内部样式或复制改版。
- 复用项目令牌、组件和布局入口，业务页面不散落重复颜色、间距、尺寸和层级值。缺少系统时只建立当前任务所需的最小公共定义。
- 新增令牌或通用组件应有稳定语义或真实复用价值；一次性、内容驱动的布局值可在局部解释，不为绕过规则制造单次 token。共享尺度和语义色仍统一管理。
- 图表、媒体算法和外部品牌色等必要例外集中在对应能力入口，不混入普通主题色。

## 布局、层级与主题

- 优先用间距和排版分组，必要时用分隔线或容器；不堆叠卡片、边框、阴影和无目的动效。
- 对齐以眼睛看到的结果为准，不以坐标或尺寸数值相等为准。图形的视觉重心和几何边界不一致时按视觉效果补偿，如圆形按钮里的三角形图标、图标与相邻文字的基线、自带留白的图标、圆角与直角相邻的边缘；补偿值在组件内部说明原因。用实际渲染的截图核对，不只核对数值。
- 主题通过统一语义入口切换，不在各组件复制配色分支；状态不能只靠颜色表达。

## 文案与说明

- 选项、设置、按钮等控件的补充性描述、副标题、说明小字、helper text 或 tooltip，只有用户明确要求时才能在要求范围内新增或扩写。要求新增功能、选项或优化界面，不等于要求增加说明文案。
- 未明确要求时直接省略此类说明，优先用准确标签和合适控件表达用途；不能因“有帮助”“更完整”或“怕用户不理解”自行添加，也不能转移到 placeholder、信息图标或其他位置变相添加。
- 获准添加的说明必须面向产品用户，用简短、自然的语言表达操作、结果或用户关心的后果；不使用开发者口吻，不讲内部协议、算法、日志、技术实现或设计过程。标签已表达清楚的内容不再复述。
- 控件标签、实际运行状态、校验错误和操作结果仍按交互需求提供，并使用面向用户的语言；不能把功能介绍或实现解释包装成状态、错误或提示来绕过上述限制。placeholder 不能替代标签。
- 以下是用户完成操作所必需的信息，不算补充性说明，无需另行要求：不可逆或高代价操作在确认时的后果；不知道就无法正确填写的格式、范围或限制；请求系统权限时的用途；无文字控件的无障碍标签；空状态下当前无内容的原因和下一步操作。每处只写必需的那一句，不借此扩写功能介绍。

## 设计方案

用户要设计图、草图或视觉方案，而设计尚未确定时，同时给出两版：保守版贴合现有设计系统和同类产品的惯例；创新版在布局、层级或交互上做出明确突破，不是换个颜色。分别说明取舍，由用户选择或混合。设计已经确定、只需实现时不适用。

- 方案、草图和原型用单个自包含的 HTML 文件呈现，多个方案并排放在同一页，不用文字描述或字符画代替。需要调参数的地方（动画时长、间距、颜色）做成可拖动的控件，并提供复制当前参数的按钮。最终界面不是网页时同样先用 HTML 定稿，再用项目的技术栈实现。设计稿不是交付代码：放进项目上下文登记的设计稿目录；没有登记时放在不会被提交的位置并告知路径。
- 没有设计系统、用户也没有给出风格方向时，避开 AI 常见的默认风格：米白或奶油色背景、标题里的斜体强调词、“01 / 02 / 03”式的章节编号、等宽字体标签、胶囊形按钮、Inter 字体配紫色渐变。只说“不要千篇一律”没有用，要点名具体样式。已确认的设计系统本来就使用的样式不受此限。用户否掉的样式记入项目上下文，后续不再出现。

## 组件与交互

- 展示组件表达数据与意图，业务规则和特权能力通过项目正式入口调用；不因 UI 改动另建平行状态源。
- 加载、空、错误、禁用与成功反馈沿用一致语义。
- 取消、卸载或并发更新涉及异步结果时防止旧结果覆盖新状态；危险动作按可撤销性和授权边界处理。
- 动效帮助解释状态，尊重减少动效偏好。

验证范围由测试规则统一决定。局部文案不触发全站主题检查；共享视觉定义变化才覆盖相关消费者。

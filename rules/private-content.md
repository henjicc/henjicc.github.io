# 私人内容不进仓库

> 读取时机：任何会修改仓库文件的任务，在第一次改动前。

什么内容属于项目、什么不该进仓库，判断标准和替代做法以 [`AGENTS.md`](../AGENTS.md) 的“私人内容不进仓库”一节为准，本文件说明门禁怎么用，以及发现已经泄漏时怎么处理。

泄漏通常发生在做界面草稿、截图验收、写任务记录、造测试数据时，为省事直接用了手边的真实文件和真实路径；所以要在写文件时就避开，门禁只是最后一道。

## 门禁

[`.githooks/pre-commit`](../.githooks/pre-commit) 在提交前检查，命中即拦，自身任何一步出错也按拦截处理：

- 媒体、字幕和办公文档（按扩展名），以及任何内容为二进制的文件（压缩包、UTF-16 文本、没列出的格式），不在 [`.githooks/media-allowlist`](../.githooks/media-allowlist) 登记的目录里。
- 文件名或本次新增的行里出现本机信息：本机用户的主目录、仓库所在目录（含工作树所属的主仓库）、登记的私人路径和词条。路径的正反斜杠、URL 编码和会话目录名写法都认。
- 文件名或本次新增的行里出现通用特征，不依赖本机信息：macOS 和 Windows 上任何真实用户名的主目录路径（示例只能用 `demo`、`test` 这类假名或 `~` 占位，假名表在脚本开头）；内嵌的 base64 媒体。

提交时只看新增的行，历史遗留内容不拦无关提交。加 `--all` 检查索引里全部已跟踪文件，用于盘点和 CI。邮箱不在默认拦截范围，不想公开的邮箱登记为词条。

钩子拦不到的情况，要靠提交前自己看和 CI：

- 别的设备上的 Linux 主目录、别的设备上主目录的 URL 编码和会话目录名写法，认不出来；把那台设备的主目录登记为私人路径。
- 无冲突的合并、rebase、cherry-pick 不触发 pre-commit，提交信息也不经过它。有冲突的合并提交时，合并进来的行都算新增。
- Jupyter 笔记本输出里的图片、普通文本里的私人内容。
- 用户名或检出目录是 `runner`、`node`、`/workspaces/…` 这类容器和 CI 通用值时，不当作本机信息。

- 钩子靠 `git config core.hooksPath .githooks` 启用，每个克隆要各做一次。开始改动前用 `git config core.hooksPath` 确认，未启用就启用；项目已有其他钩子管理工具时，改为在其 pre-commit 中调用该脚本。
- 钩子猜不到的本机信息要登记，值存在 `.git/config`，不进仓库，各工作树共用。任务中得知这类信息时主动登记，不写进任何已跟踪文件：
  - 目录用 `git config --add privatecheck.path "<目录>"`，如数据目录、素材盘路径；各种分隔写法都会拦。至少两级，盘符根目录太宽不生效，脚本会给出警告。
  - 词条用 `git config --add privatecheck.term "<词条>"`，如真实姓名、手机号、私人邮箱、客户与合作方名字、作品标题；按原文匹配，不分大小写。
- 白名单登记的是项目放资源、测试素材和文档配图的目录，不是用来放行单个文件的。登记前按 `AGENTS.md` 的两问确认目录里的内容属于项目；不为让某个文件通过而登记宽泛的目录（如仓库根目录）。
- 不用 `--no-verify`、`git add -f` 或改 `core.hooksPath` 绕过，也不为让提交通过而放宽脚本或白名单。确属误报时向用户说明命中内容，由用户决定怎么改。
- 改动脚本后运行 `.githooks/selftest`，它在临时仓库里构造应拦和应放行的提交并核对结果；换到新系统上第一次使用时也跑一次。

## 给项目接入防线

初始化时，或给已有项目补上这套防线时：

1. 把模板的 `.githooks/`、`.gitattributes` 里固定钩子换行的一行、`.gitignore` 里的 `/.local/`、本文件、`AGENTS.md` 的“私人内容不进仓库”一节和 [`experience/repo-privacy-cleanup.md`](experience/repo-privacy-cleanup.md) 并入项目，保留项目已有约定。确认钩子文件有可执行位。
2. 启用钩子并运行 `.githooks/selftest`。项目有安装步骤时让它自动启用钩子。有 CI 时加跑 `.githooks/pre-commit --all`；钩子没启用、没有可执行位或被绕过时，这是唯一的兜底。
3. 向用户问明数据目录、素材盘和需要保密的名字，登记为私人路径和词条。
4. 按经验文件的“盘点”一节检查已跟踪内容和历史，把清单交给用户定范围；盘点期间只报告不修改。
5. 用户确认后清理当前版本，把确属项目的媒体目录登记进白名单，直到 `--all` 通过。

## 发现已经进了仓库

发现已跟踪文件或历史里有不该进仓库的内容时，停止推送，向用户报告具体文件、所在提交和仓库的公开状态。清理当前版本和改写历史的做法与坑见 [`experience/repo-privacy-cleanup.md`](experience/repo-privacy-cleanup.md)；改写历史、强制推送、改仓库可见性每一步都要用户明确同意，不自行处理。
